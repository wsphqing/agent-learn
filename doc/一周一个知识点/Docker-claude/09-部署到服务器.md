# 第 9 章 · 实战总装：把项目部署到服务器

> 本章目标：把实战项目真正部署到一台 Linux 云服务器上，加 Nginx 反向代理，配置自动重启，并走通"更新上线"的完整流程。这是全书的综合实战。

---

## 9.1 部署全景图

```
  你的 Mac (开发)                镜像仓库              云服务器 (Linux)
 ┌──────────────┐            ┌──────────┐           ┌────────────────────┐
 │ 1. 写代码      │            │          │           │ 4. docker compose  │
 │ 2. buildx 构建 │ ──push──▶ │ Docker   │ ──pull──▶ │    pull & up -d     │
 │   (多架构)     │            │ Hub      │           │ 5. Nginx 反代对外    │
 │ 3. push 镜像   │            │          │           │    域名/端口访问      │
 └──────────────┘            └──────────┘           └────────────────────┘
```

我们要做的事：
1. 准备一台 Linux 云服务器并装好 Docker。
2. 把实战项目的 compose 文件改造成"生产版"（用仓库镜像而非本地构建）。
3. 在服务器上拉起整套服务。
4. 加一个 Nginx 反向代理，把前端和后端 API 收敛到一个入口。
5. 配置开机自启和崩溃自动重启。

## 9.2 准备服务器并安装 Docker

**第 1 步：搞一台云服务器**
随便哪家云厂商（阿里云、腾讯云、AWS、DigitalOcean 等），开一台 **Ubuntu 22.04 / 24.04** 的 x86_64 服务器，SSH 登录进去。

```bash
ssh root@你的服务器IP
#   用 ! 前缀可在本会话里直接跑：! ssh root@你的服务器IP
```

**第 2 步：在服务器上安装 Docker**（Ubuntu 官方便捷脚本）：

```bash
# 以下命令在【服务器】上执行
curl -fsSL https://get.docker.com -o get-docker.sh   # 下载官方安装脚本
sudo sh get-docker.sh                                # 执行安装（会自动装 docker + compose 插件）
sudo docker --version                                # 验证
sudo docker compose version                          # 验证 compose
```

**第 3 步（可选）：让当前用户免 sudo 用 docker**：
```bash
sudo usermod -aG docker $USER    # 把当前用户加入 docker 组
#   ⚠️ 需要重新登录（退出再 ssh 进来）才生效
```

> ⚠️ **安全红线**：`docker` 组权限等同于 root（能挂载宿主机任意目录）。生产服务器上谨慎授予，别随便给不信任的用户。

## 9.3 改造成"生产版" Compose 并部署

开发用的 compose 有 `build:`（本地构建）和绑定挂载（热更新），**生产环境不要这些**——生产应该用**已经推到仓库的镜像**。

**第 1 步：在本地把镜像推上去**（承接第 8 章，注意多架构）：

```bash
# 在【本地 Mac】执行
docker buildx build --platform linux/amd64,linux/arm64 \
  -t 你的用户名/todo-backend:1.0 --push ./backend
docker buildx build --platform linux/amd64,linux/arm64 \
  -t 你的用户名/todo-frontend:1.0 --push ./frontend
```

**第 2 步：写生产版 `docker-compose.prod.yml`**（上传到服务器）：

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}     # 从服务器上的 .env 读
      POSTGRES_DB: tododb
    volumes:
      - todo-pgdata:/var/lib/postgresql/data
    restart: always                               # ★ 崩溃/重启后自动拉起（见 9.5）
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5
    # ★ 生产环境【不】对外暴露数据库端口！删掉 ports，只在内部网络可达，更安全

  redis:
    image: redis:7-alpine
    restart: always
    volumes:
      - todo-redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

  backend:
    image: 你的用户名/todo-backend:1.0            # ★ 用仓库镜像，不再 build
    environment:
      DATABASE_URL: postgres://postgres:${POSTGRES_PASSWORD}@db:5432/tododb
      REDIS_URL: redis://redis:6379
      PORT: 3000
    restart: always
    depends_on:
      db: { condition: service_healthy }
      redis: { condition: service_healthy }
    # ★ 不直接对外暴露 3000，交给下面的 nginx 反代

  frontend:
    image: 你的用户名/todo-frontend:1.0           # ★ 用仓库镜像
    restart: always
    depends_on:
      - backend

  nginx:                                          # ★ 新增：反向代理，唯一对外的入口
    image: nginx:1.27-alpine
    ports:
      - "80:80"                                   # 只有它对外暴露 80 端口
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro   # 挂载我们的反代配置（只读）
    restart: always
    depends_on:
      - frontend
      - backend

volumes:
  todo-pgdata:
  todo-redisdata:
```

**第 3 步：在服务器上建 `.env`**：

```bash
# 在【服务器】上，compose 文件同目录
echo "POSTGRES_PASSWORD=一个很强的生产密码" > .env
#   ⚠️ 生产密码要强、要保密，别和开发环境一样
```

## 9.4 加一个 Nginx 反向代理

**为什么要反代**：现在前端在一个容器、后端在另一个容器，端口各不相同。我们希望用户**通过一个域名/端口（80）** 访问：`/` 走前端页面，`/api` 走后端。Nginx 反代负责这个"分流"。

在服务器上创建 `nginx.conf`（和 compose 同目录）：

```nginx
server {
    listen 80;                          # nginx 监听 80 端口
    server_name _;                      # 匹配所有域名（有域名可填你的域名）

    # 前端：根路径转发给 frontend 容器
    location / {
        proxy_pass http://frontend:80;  # ★ 直接用服务名 frontend 当主机名（同一 compose 网络）
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 后端 API：/api 开头的转发给 backend 容器
    location /api/ {
        proxy_pass http://backend:3000/;  # ★ 服务名 backend；末尾 / 会把 /api/ 前缀去掉
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

- `proxy_pass http://frontend:80` 里的 `frontend` 就是 compose 的服务名，能直接解析（第 6、7 章的机制）。
- `/api/` 的转发末尾带 `/`，表示把 `/api/db` 重写成后端的 `/db`。

## 9.5 启动 + 自动重启 + 开机自启

**启动整套**（在服务器 compose 目录）：

```bash
docker compose -f docker-compose.prod.yml up -d
#   -f 指定用生产版 compose 文件
#   它会自动从 Docker Hub pull 你的 backend/frontend 镜像，以及 postgres/redis/nginx
```

✅ **预期输出**：5 个服务（db、redis、backend、frontend、nginx）陆续拉取镜像并启动。

**验证**：
```bash
docker compose -f docker-compose.prod.yml ps      # 5 个服务都 Up，db/redis healthy
curl http://localhost/api/db                       # 经 nginx → backend → db
#   预期：{"db":"connected","now":"..."}
```

**从你自己的电脑浏览器访问 `http://你的服务器IP`**：
✅ **预期输出**：看到前端页面。访问 `http://你的服务器IP/api/db` 返回数据库连通的 JSON。**整套应用上线了！** 🎉

### `restart` 策略详解

compose 里每个服务都加了 `restart: always`，这解决两个问题：**容器崩溃自动拉起** + **服务器重启后自动恢复**。

| 策略 | 含义 |
|------|------|
| `no`（默认） | 不自动重启 |
| `on-failure` | 只有非正常退出（退出码非 0）时重启 |
| `always` | 总是重启，**包括 Docker 服务（宿主机）重启后也自动拉起** ★ |
| `unless-stopped` | 同 always，但如果是你手动 stop 的，就不自动拉起 |

**生产推荐 `always` 或 `unless-stopped`。** 配合 Docker 本身的开机自启（`get.docker.com` 脚本装的 Docker 默认已设 `systemctl enable docker`），服务器重启后整套应用会自动回来。

## 9.6 更新上线的正确姿势

以后改了代码要上线，标准流程是：

```bash
# === 在本地 Mac ===
# 1. 改代码，构建新版本镜像（建议用新 tag，便于回滚）
docker buildx build --platform linux/amd64,linux/arm64 \
  -t 你的用户名/todo-backend:1.1 --push ./backend

# === 在服务器 ===
# 2. 改 compose 文件里的 tag：todo-backend:1.0 → 1.1（或用变量管理）
# 3. 拉取新镜像并重建对应服务
docker compose -f docker-compose.prod.yml pull backend   # 拉新镜像
docker compose -f docker-compose.prod.yml up -d          # 只重建有变化的服务（backend），其他不动
```

- Compose 足够聪明：`up -d` 时只有镜像/配置变了的服务会被重建，没变的（如 db）保持不动、不中断。
- ⚠️ **用明确 tag（1.0 → 1.1）而不是 `latest`**，这样出问题能快速改回 `1.0` 回滚。
- 更彻底的零停机/灰度发布需要更复杂的编排（这正是 K8s 擅长的，见第 11 章）。

**清理旧镜像**（更新多了本地会堆积）：
```bash
docker image prune -f     # 清理悬空镜像（见第 10 章）
```

## 9.7 🔨 实战项目收尾：完整走一遍上线

串起本章所有步骤，完成从本地到线上的全流程（**这是实战项目的终点**）：

1. **本地**：`docker buildx build --platform linux/amd64,linux/arm64 -t 你的用户名/todo-backend:1.0 --push ./backend`，前端同理。
2. **服务器**：装好 Docker；上传 `docker-compose.prod.yml` + `nginx.conf`；建好 `.env`。
3. **服务器**：`docker compose -f docker-compose.prod.yml up -d`。
4. **验证**：浏览器访问 `http://服务器IP` 看到前端；`http://服务器IP/api/db` 返回数据库 JSON。
5. **模拟崩溃恢复**：`docker kill $(docker compose -f docker-compose.prod.yml ps -q backend)` 杀掉后端容器，过几秒 `docker compose -f docker-compose.prod.yml ps` 看它因 `restart: always` **自动重启**回来了。

✅ **最终预期**：
- `http://服务器IP` 能打开前端页面。
- `http://服务器IP/api/db` 返回 `{"db":"connected",...}`。
- 杀掉后端容器后它能自动恢复。

做到这三点，**你已经具备独立把项目容器化部署上线的能力了**——这是本文档最核心的目标达成！

> 🎯 **自检**：为什么生产版 compose 里数据库**不**对外暴露端口（去掉了 `ports`）？（答：安全。数据库只需被内部的 backend 通过服务名访问，对公网暴露 5432 会被扫描攻击。）为什么用 Nginx 反代而不让前端后端各自暴露端口？（答：统一入口、便于加 HTTPS/限流/路由，用户只需记一个地址。）

## ✅ 本章小结

- 部署链路：本地 buildx 构建多架构镜像 → push → 服务器 pull → `compose up -d`。
- **生产版 compose 与开发版的区别**：用仓库 `image` 而非 `build`、去掉绑定挂载热更新、数据库**不对外暴露端口**、加 `restart: always`、加 Nginx 反代统一入口。
- **Nginx 反向代理**用服务名转发，把前端 `/` 和后端 `/api` 收敛到一个 80 端口。
- `restart: always` 实现崩溃自愈 + 开机自启；Docker 本身默认已开机自启。
- 更新上线：构建新 tag → push → 服务器 `pull` + `up -d`，只重建变化的服务，**用明确 tag 便于回滚**。
- **你已经完整走通了一个全栈应用的容器化部署上线全流程。**
