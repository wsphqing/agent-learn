# 第 10 章 · 日常维护与排错

> 本章目标：掌握清理磁盘、排查容器起不来、限制资源、基本安全的实用技能。这些是让你能长期稳定用 Docker 的"运维内功"。

---

## 10.1 ⚠️ 磁盘被 Docker 吃满了怎么办

用 Docker 一段时间后，你很可能遇到磁盘告急。因为 Docker 会攒下大量：**停止的容器、无用的镜像、悬空的卷、构建缓存**。

**第 1 步：看 Docker 占了多少空间**

```bash
docker system df
#   预期输出：分类列出 Images / Containers / Local Volumes / Build Cache 各占多少，
#            以及有多少是 RECLAIMABLE（可回收的）
```

**输出示例解读**：
```
TYPE            TOTAL   ACTIVE   SIZE      RECLAIMABLE
Images          25      4        8.5GB     6.2GB (72%)      ← 25个镜像，只有4个在用，6.2GB可回收
Containers      12      2        1.1GB     1.0GB (90%)      ← 12个容器，10个已停止
Local Volumes   8       3        3.2GB     2.1GB (65%)
Build Cache     40      0        4.8GB     4.8GB            ← 构建缓存也占不少
```

**第 2 步：按需清理**

```bash
docker container prune      # 删除所有【已停止】的容器
docker image prune          # 删除【悬空镜像】（没有 tag、没被引用的 <none> 镜像）
docker image prune -a       # ⚠️ 删除所有【未被容器使用】的镜像（更狠，慎用）
docker volume prune         # 删除所有【未被使用】的卷 ⚠️ 可能含你以为还要的数据！
docker builder prune        # 清理构建缓存
docker network prune        # 删除未使用的自定义网络
```

**核弹级一键清理**：

```bash
docker system prune
#   一次清理：停止的容器 + 悬空镜像 + 未使用的网络 + 构建缓存（不含卷，相对安全）

docker system prune -a --volumes
#   ⚠️⚠️ 最狠：连未使用的镜像和【卷】一起删。卷里可能有数据库数据！执行前务必想清楚
```

> ⚠️ **重灾区提醒**：
> - `docker volume prune` 和 `--volumes` 会删卷，**卷里可能是你的数据库数据**。删之前确认这些卷真的不要了。正在被容器使用的卷不会被删，但**已停止/删除容器留下的卷**会被清掉。
> - `docker image prune -a` 会删掉所有当前没有容器在用的镜像，下次要用得重新 pull/build。
> - 日常建议只用温和的 `docker system prune`（不带 `--volumes`），定期跑跑就行。

## 10.2 容器起不来 / 表现异常的排查套路

遇到容器起不来、一直重启、或行为诡异，按这个顺序排查：

**① 先看状态**
```bash
docker ps -a
#   看目标容器的 STATUS：
#   - Exited (0)    正常退出（可能是主进程干完就退了，见第2章坑1）
#   - Exited (1/137/...) 非正常退出，1一般是应用报错，137是被 OOM/kill
#   - Restarting    在反复重启（通常是启动就崩，配了 restart 策略在打转）
```

**② 看日志（最重要！90% 的问题看日志就明白）**
```bash
docker logs 容器名          # 看全部日志
docker logs --tail 50 容器名 # 只看最后 50 行
docker logs -f 容器名        # 持续跟随
#   ★ 应用崩溃的报错、连不上数据库的错误、端口占用，几乎都会打在日志里
```

**③ 看容器详细配置**
```bash
docker inspect 容器名
#   输出一大坨 JSON：挂载了哪些卷、接了哪些网络、环境变量、启动命令、退出码原因等
#   排查"挂载路径不对""环境变量没传对""网络没接上"时很有用
docker inspect -f '{{.State.ExitCode}}' 容器名   # 用 -f 只提取退出码
```

**④ 进容器内部看看（如果容器还活着）**
```bash
docker exec -it 容器名 sh
#   进去检查文件在不在、环境变量对不对、能不能 ping 通别的服务
#   （容器已退出就进不去，这时用下面的办法）
```

**⑤ 容器起不来、连 exec 都进不去时——用镜像开个临时容器调试**
```bash
docker run --rm -it --entrypoint sh 你的镜像名
#   --entrypoint sh 强行覆盖启动命令，直接进 shell，绕过那个会崩的主进程
#   进去后手动敲原本的启动命令，看它到底报什么错
```

**⑥ 看 Docker 事件流（进阶）**
```bash
docker events        # 实时打印 Docker 的事件（容器 start/stop/die/oom 等），另开终端观察
```

**常见问题速判**：

| 现象 | 大概率原因 | 查法 |
|------|-----------|------|
| `Exited (0)` 秒退 | 主进程干完就结束（非服务型） | 回顾第 2 章坑 1 |
| `Exited (1)` | 应用代码报错 | `docker logs` |
| `Exited (137)` | 被 OOM 杀掉（内存超限） | 看内存限制、`docker inspect` |
| 一直 `Restarting` | 启动即崩 + restart 策略在打转 | `docker logs` 看崩溃原因 |
| 端口连不上 | 没映射/服务监听 127.0.0.1 | 回顾第 6 章坑 4 |
| 连不上其他容器 | 不在同一网络/用了 localhost | 回顾第 6 章 |

## 10.3 资源限制

默认容器可以用光宿主机的所有资源，一个失控的容器能拖垮整台机器。可以限制：

```bash
docker run -d \
  --memory=512m \
  --cpus=1.5 \
  --name limited-app my-image
# 参数解释：
#   --memory=512m   最多用 512MB 内存。超了会被 OOM killer 杀掉（表现为 Exited 137）
#   --cpus=1.5      最多用 1.5 个 CPU 核心
```

Compose 里的写法：

```yaml
services:
  backend:
    image: my-backend
    deploy:
      resources:
        limits:
          memory: 512M       # 内存上限
          cpus: '1.5'        # CPU 上限
```

> 💡 给关键服务设资源上限是良好习惯，能防止某个服务内存泄漏拖垮整机，也让容量规划更可控。

## 10.4 安全小贴士

容器不是绝对安全的沙箱，几条基本原则务必遵守：

1. **别用 root 跑应用** ⚠️
   容器里默认是 root。一旦应用被攻破，攻击者在容器里就是 root，风险更大。在 Dockerfile 里切换到普通用户：
   ```dockerfile
   RUN addgroup -S app && adduser -S app -G app   # 创建普通用户（alpine 语法）
   USER app                                        # 之后以 app 用户运行
   ```

2. **绝不要把密钥打进镜像** ⚠️⚠️
   不要 `COPY .env`、不要把密码 `ENV PASSWORD=xxx` 写死在 Dockerfile。镜像的每一层都会被保存，**即使后面删了，密钥仍藏在历史层里**能被扒出来。密钥用**运行时环境变量**（`-e` / compose 的 `environment` + `.env`）或专门的 secrets 机制注入。

3. **用官方/可信镜像，钉死版本**
   基础镜像用官方镜像（Docker Hub 上带 "Official" 标记的）；用明确 tag（`node:20.11-alpine`）而非 `latest`，避免供应链风险和不可复现。

4. **定期更新基础镜像**
   基础镜像会有安全补丁。定期重新 `pull` 基础镜像并重新构建，别一个镜像用两年。

5. **最小化镜像内容**
   镜像里工具越少，攻击面越小。这也是 distroless/alpine 受青睐的安全理由（第 4 章）。

6. **别把 Docker socket 挂进不可信容器**
   `-v /var/run/docker.sock:...` 等于把宿主机的控制权交出去，等同 root，除非你非常清楚在干什么。

## 10.5 🔨 跟着敲一遍：清理磁盘

```bash
# 1. 先看看当前占用
docker system df
#   记下 RECLAIMABLE 那列的数字

# 2. 造一点垃圾（构建后删掉容器，留下悬空镜像）
docker pull alpine:3.19
docker pull alpine:3.18
docker run --name tmp1 alpine:3.19 echo hi     # 跑完即退，留下一个停止的容器
docker run --name tmp2 alpine:3.18 echo hi

# 3. 看看停止的容器
docker ps -a | grep tmp                         # 能看到 tmp1、tmp2 都是 Exited

# 4. 清理停止的容器
docker container prune -f
#   -f 跳过确认。预期：提示 Deleted Containers，并报告回收的空间

# 5. 确认清理效果
docker ps -a | grep tmp                         # 预期：没有输出了，tmp1/tmp2 已删除
docker system df                                # 预期：Containers 的数量/占用下降
```

✅ **预期结果**：`docker container prune` 后，`docker ps -a` 里刚才那两个 `tmp` 容器消失，`docker system df` 显示容器占用下降。

清理刚才拉的测试镜像：
```bash
docker rmi alpine:3.19 alpine:3.18
```

> 🎯 **自检**：`docker system prune` 和 `docker system prune -a --volumes` 的区别是什么？哪个有丢数据的风险？（答：前者清停止容器+悬空镜像+网络+构建缓存，不动卷，相对安全；后者连未使用镜像和卷一起删，卷里可能有数据库数据，有丢数据风险。）

## ✅ 本章小结

- **磁盘管理**：`docker system df` 看占用，`docker system prune` 温和清理；⚠️ 带 `--volumes` 会删卷（可能含数据），慎用。
- **排错套路**：`ps -a` 看状态 → **`logs` 看日志（最关键）** → `inspect` 看配置 → `exec` 进容器 → 起不来就 `--entrypoint sh` 开临时容器调试。
- 记住退出码：`0` 正常、`1` 应用报错、`137` 被 OOM 杀。
- **资源限制**：`--memory` / `--cpus` 防止单个容器拖垮整机。
- **安全六条**：别用 root、别把密钥打进镜像、用可信镜像钉版本、定期更新、最小化、别乱挂 docker socket。
