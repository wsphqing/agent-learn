# 第 2 章 · 镜像与容器（核心基石）

> 本章目标：彻底分清「镜像」和「容器」，理解镜像分层机制，并掌握管理容器的一整套高频命令。这是全书的地基。

---

## 2.1 镜像（Image）：一句话解释

> **镜像 = 一个"打包好的、只读的应用环境模板"。**

生活类比：镜像就像**菜谱 + 一份预制好的半成品套装**。它规定好了一切（用什么底料、放了哪些配料），但它本身只是个模板，**不会自己动**。

技术上，镜像里包含：

- 一个精简的操作系统文件层（比如基于 Alpine 或 Debian）
- 你的应用运行时（Node、JRE、Go 编译好的二进制……）
- 你的应用代码
- 依赖库、环境变量、以及"启动时该执行什么命令"

镜像是**只读**的、**不可变**的。你把它 pull 下来是什么样，跑起来就是什么样。

---

## 2.2 容器（Container）：一句话解释

> **容器 = 镜像"跑起来"的那个活的实例。**

接着上面的类比：容器就是**照着菜谱真正做出来、端上桌的那盘菜**。同一份菜谱（镜像）可以做出很多盘菜（容器）。

技术上，容器 = **镜像（只读层） + 一个可写层 + 一个正在运行的进程**。当容器运行时对文件系统做修改（创建文件、写日志），这些改动写在**最上面那个薄薄的可写层**里，底下的镜像层纹丝不动。

### 容器的生命周期

```
   created ──start──▶ running ──stop──▶ stopped(exited)
      ▲                  │  ▲              │
      │                  │  └──start───────┘   ← stopped 的容器可以再 start 回来
   create              pause/unpause
                                            
   stopped ──rm──▶ (彻底删除，不复存在)
```

- **created**：已创建但没运行。
- **running**：运行中（`docker ps` 能看到）。
- **stopped / exited**：进程结束或被停止。**注意：停止 ≠ 删除**，容器还在，可以 `start` 重新拉起，数据也还在。
- **删除（rm）**：这才是彻底移除，之后就找不回了。

> 💡 回顾第 0 章的直觉：**容器的核心是"运行一个进程"。这个进程结束，容器就从 running 变成 exited。**

---

## 2.3 ⚠️ 最重要的对比：镜像 vs 容器

新手最容易混这两个。用表格钉死它：

| 维度 | 镜像（Image） | 容器（Container） |
|------|--------------|------------------|
| **是什么** | 静态的、打包好的模板 | 镜像运行起来的动态实例 |
| **可变性** | 只读，不可变 | 有一个可写层，运行时可改动 |
| **数量关系** | 1 个镜像 | 可以起出 N 个容器 |
| **类比（编程）** | 类（Class）、可执行文件 | 对象（Instance）、进程 |
| **类比（生活）** | 菜谱 / 模具 | 做出来的菜 / 铸出来的零件 |
| **用什么命令看** | `docker images` | `docker ps` |
| **怎么产生** | `docker build` 或 `docker pull` | `docker run`（从镜像创建） |
| **删除命令** | `docker rmi` | `docker rm` |

**一句话**：镜像是"名词、静态、模板"；容器是"动词、动态、实例"。`run` 就是把镜像这个模板"实例化"成一个活容器的动作。

---

## 2.4 镜像分层（Layer）机制

这是 Docker 省空间、构建快的秘密，理解它对第 4 章的优化至关重要。

**镜像不是一整块，而是由多个只读层（layer）叠起来的。** 每一层都是在前一层基础上的"增量改动"。

举例，一个 Node 应用镜像可能是这样叠出来的：

```
┌───────────────────────────┐
│ 第4层：COPY 你的应用代码进来   │  ← 只包含"新增了代码"这个改动
├───────────────────────────┤
│ 第3层：npm install 装的依赖   │  ← 只包含"新增了 node_modules"
├───────────────────────────┤
│ 第2层：装了 Node 运行时       │
├───────────────────────────┤
│ 第1层：基础系统（如 alpine）   │  ← 最底层的精简 OS
└───────────────────────────┘
```

**分层带来两个巨大好处：**

1. **共享复用，省空间**：如果你有 5 个镜像都基于 `node:20-alpine`，那个基础层在磁盘上**只存一份**，5 个镜像共享它。你 pull 第二个 node 镜像时会看到很多层显示 `Already exists`，就是在复用。

2. **缓存加速，构建快**：改代码时通常只有最上面"COPY 代码"那层变了，下面装依赖、装 Node 的层没变，可以直接复用缓存，不用重跑。（第 4 章会把这一点玩出花。）

> 💡 容器运行时那个"可写层"，就是叠在这些只读层最上面的第 5 层。这也解释了为什么 `--rm` 删掉容器数据就没了——数据在可写层，容器一删，可写层就没了，而只读的镜像层不受影响。

## 2.5 镜像的命名规则

看这个镜像名，把它拆开：

```
registry.example.com/library/nginx:1.27-alpine
└────────┬────────┘ └──┬──┘ └─┬─┘ └────┬────┘
     仓库地址        命名空间  镜像名     标签(tag)
   (省略则为          (用户/     (仓库)   (版本/变体)
    Docker Hub)       组织名)
```

- **标签（tag）**：区分版本或变体，比如 `1.27`、`alpine`、`latest`。
- ⚠️ **`latest` 的陷阱**：不写 tag 时默认是 `latest`。但 `latest` **不代表"最新"**，它只是"没指定 tag 时的默认名字"。它今天指向的版本和下个月可能不一样，会导致"构建不可复现"。**生产环境永远要写明确的版本 tag**，比如 `node:20.11-alpine`，而不是 `node` 或 `node:latest`。
- **`-alpine` 后缀**：表示基于 Alpine Linux（一个极小的发行版，约 5MB）构建的变体，体积小很多。第 4 章细讲怎么选。

## 2.6 高频命令逐行详解

下面这些命令是你**每天都要用**的，务必敲熟。

### 找镜像、拉镜像、看镜像

```bash
docker pull nginx:1.27-alpine   # ← 从仓库拉取指定镜像到本地。不写 tag 默认拉 latest
docker images                   # ← 列出本地所有镜像（仓库名、tag、镜像ID、大小）
docker rmi nginx:1.27-alpine    # ← 删除本地镜像（rmi = remove image）
```

### 运行容器：`docker run` 及其高频参数

`docker run` 是最核心的命令，参数最多，这里把高频的讲透：

```bash
docker run -d --name web -p 8080:80 nginx:1.27-alpine
# 逐个参数解释：
#   -d               后台运行（detached）。不加 -d 会占着你的终端打印日志
#   --name web       给容器起个名字叫 web（不起名的话 Docker 会随机分配一个滑稽的名字）
#   -p 8080:80       端口映射：把宿主机的 8080 端口 → 容器内的 80 端口
#                    （格式永远是"宿主机端口:容器端口"，别记反！详见第6章）
#   nginx:1.27-alpine 用哪个镜像
```

其他高频参数：

```bash
docker run -it --rm ubuntu:22.04 bash
#   -it    交互式终端（-i 保持输入 + -t 分配终端），常用于进容器调试
#   --rm   容器退出后自动删除自己，适合一次性任务

docker run -d -e POSTGRES_PASSWORD=secret --name pg postgres:16
#   -e KEY=VALUE   设置环境变量（可多次使用 -e）。很多镜像靠环境变量配置，如数据库密码
```

### 查看、进入、停止、删除容器

```bash
docker ps                    # ← 列出【正在运行】的容器
docker ps -a                 # ← 列出【所有】容器（含已停止的）。-a = all

docker logs web              # ← 查看名为 web 的容器的日志（排错第一利器！）
docker logs -f web           # ← -f 持续跟随输出（follow），像 tail -f，Ctrl+C 退出

docker exec -it web sh       # ← 进入正在运行的 web 容器，开一个 sh 终端来看看里面
#   exec   在【运行中】的容器里执行命令
#   -it    交互式终端
#   sh     要执行的命令（alpine 镜像通常只有 sh，没有 bash）

docker stop web              # ← 优雅停止容器（发 SIGTERM，等它自己收尾）
docker start web             # ← 重新启动一个已停止的容器
docker restart web           # ← 重启

docker rm web                # ← 删除容器（必须先 stop，或用 -f 强制）
docker rm -f web             # ← -f 强制删除（会先杀掉再删）
```

### 一次性清理（常用组合）

```bash
docker rm -f $(docker ps -aq)   # ← 强制删除所有容器
#   docker ps -aq   -a 所有 + -q 只输出容器ID（quiet），把ID列表喂给 docker rm -f
```

## 2.7 ⚠️ 常见坑与易错点

**坑 1：容器一启动就退出了**

```bash
docker run -d ubuntu:22.04    # ← 起完立刻就 Exited 了，docker ps 里根本看不到
```
**原因**：容器的命脉是"那个主进程"。`ubuntu` 镜像默认启动的是 bash，但你 `-d` 后台运行且没有交互终端，bash 没事干立刻退出 → 主进程结束 → 容器退出。
**结论**：**容器不是"开机的机器"，而是"运行一个前台进程"。主进程结束，容器就死。** 像 nginx、postgres 这些镜像能一直运行，是因为它们的主进程是"一直不退出的服务"。

**坑 2：端口映射记反了**

`-p 8080:80` 是 `宿主机:容器`。想在浏览器用 8080 访问，容器内服务监听的是 80，就必须写 `8080:80`。写成 `80:8080` 就连不上。**口诀：左边是你（宿主机）从外面敲的门，右边是容器里服务实际开的门。**

**坑 3：`docker exec` 进不去 / 报错**

- 如果报 `No such container`，多半是容器已经退出了（`exec` 只能进**运行中**的容器）。先 `docker ps -a` 看状态。
- 如果报 `bash: not found`，是因为该镜像（比如 alpine 系）没装 bash。改用 `sh`：`docker exec -it xxx sh`。

**坑 4：`docker rm` 删不掉**

运行中的容器不能直接 `rm`，会报错。要么先 `docker stop`，要么 `docker rm -f` 强制删。

## 2.8 🔨 跟着敲一遍：用 Nginx 跑一个网页

目标：启动一个 Nginx 容器，用浏览器访问到它的欢迎页。

```bash
# 1. 后台启动一个 nginx 容器，把宿主机 8080 映射到容器 80
docker run -d --name my-nginx -p 8080:80 nginx:1.27-alpine
#   -d 后台  --name my-nginx 命名  -p 8080:80 端口映射  用 nginx alpine 镜像

# 2. 确认它在运行
docker ps
#   预期：能看到一行 my-nginx，STATUS 是 Up xx seconds，PORTS 显示 0.0.0.0:8080->80/tcp
```

**打开浏览器访问 <http://localhost:8080>**

✅ **预期输出**：看到 Nginx 的欢迎页 **"Welcome to nginx!"**。看到就说明你成功地：拉取了镜像 → 起了容器 → 做了端口映射 → 从宿主机访问到了容器内的服务。

再玩一下管理命令：

```bash
docker logs my-nginx         # ← 能看到刚才浏览器访问产生的日志（一条 GET / 请求记录）
docker exec -it my-nginx sh  # ← 进入容器内部
  ls /usr/share/nginx/html   #   （在容器里）看到 index.html 等文件，这就是那个欢迎页
  exit                       #   退出容器（容器继续在后台运行，因为你只是退出了 exec 的 shell）
```

清理：

```bash
docker stop my-nginx         # ← 停止
docker rm my-nginx           # ← 删除
# 或者一步到位：docker rm -f my-nginx
```

再访问 <http://localhost:8080> 应该就打不开了（容器没了）。

> 🎯 **自检**：你能说清楚 `-d`、`--name`、`-p 8080:80` 三个参数分别干嘛吗？能解释为什么 nginx 容器不会像坑 1 里的 ubuntu 那样秒退吗？（答：nginx 主进程是常驻服务，不会自己结束。）能答上来，本章就过关了。

## ✅ 本章小结

- **镜像 = 只读模板（菜谱）；容器 = 镜像跑起来的实例（做出来的菜）。** 一个镜像可起多个容器。
- 容器生命周期：created → running → stopped，`stop` 不等于删除，`rm` 才是真删。
- **镜像是分层的**，层可复用、可缓存，这是省空间和快构建的基础。
- 镜像命名 `仓库/名字:tag`，⚠️ 生产别用 `latest`，要钉死版本号。
- 核心命令一条线：`pull` / `images` / `run` / `ps` / `logs` / `exec` / `stop` / `rm` / `rmi`。
- 牢记：**容器的命脉是它的主进程，进程一结束容器就退出。**
