# 第 4 章 · 让镜像更专业：构建优化

> 本章目标：把镜像构建得**又快又小**。理解层缓存、掌握多阶段构建（这是你作为前端/Go 开发者最能受益的一章）。

---

## 4.1 层缓存（Layer Cache）原理

回顾第 2 章：镜像是**分层**的。再补一个关键规则——

> **`docker build` 时，Docker 会逐条执行 Dockerfile 指令。对每条指令，如果"输入没变"，就直接复用上次构建的那层缓存（显示 CACHED），跳过执行。一旦某一层缓存失效，它【以及后面所有层】都要重新构建。**

注意最后半句：**缓存失效是"一失效，后面全塌"**。这就是为什么**指令顺序至关重要**。

什么会让一层的缓存失效？

- `RUN` 指令：命令文本变了。
- `COPY` / `ADD` 指令：**被复制的文件内容变了**。
- 前面任意一层失效了（连锁反应）。

---

## 4.2 依赖安装的正确姿势

来看一个**反面教材**和**正面写法**的对比。

**❌ 反面写法（每次改代码都重装依赖）：**

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY . .              # ← 把所有代码（含 package.json）一次性拷进来
RUN npm install       # ← 装依赖
CMD ["node", "server.js"]
```

问题：你改了 `server.js` 一行代码 → `COPY . .` 这层的输入变了 → 缓存失效 → **它后面的 `RUN npm install` 也被迫重跑**。可依赖明明没变啊！每次都白等几十秒装依赖。

**✅ 正面写法（依赖和代码分开拷）：**

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./  # ← ① 先只拷依赖清单
RUN npm ci             # ← ② 装依赖（只要 package*.json 没变，这两层永远走缓存）
COPY . .               # ← ③ 再拷其余代码
CMD ["node", "server.js"]
```

现在你改 `server.js`：只有 ③ `COPY . .` 失效重跑（很快），① 和 ② 因为 `package*.json` 没变**继续走缓存**，依赖不重装。构建从几十秒变成一两秒。

> 💡 **通用原则：把"不常变的"放前面，"常变的"放后面。** 依赖清单几周才动一次，源码天天改，所以依赖装在前、代码拷在后。这个思路对 Go（先 `go mod download` 再 `COPY` 源码）、Python（先 `pip install -r requirements.txt`）完全一样。

## 4.3 多阶段构建（Multi-stage Build）

这是本章的重头戏，也是你作为**前端 + Go 开发者**最有共鸣的部分。

### 痛点：构建需要的东西，运行时根本不需要

想想两个典型场景：

- **前端项目**：需要 Node + 一堆 devDependencies 来 `npm run build`，但**构建产物只是一堆静态文件**（HTML/CSS/JS）。运行时只需要一个 Nginx 来托管这些静态文件，根本不需要 Node 和 node_modules！
- **Go 项目**：需要完整的 Go 工具链来 `go build`，但**产物只是一个二进制文件**。运行时只需要这个二进制，不需要几百 MB 的 Go SDK！

如果只用单阶段构建，你的最终镜像会背着"构建工具"这个大包袱，又臃肿又不安全。

### 解法：分成"构建阶段"和"运行阶段"

> **多阶段构建 = 在一个 Dockerfile 里用多个 `FROM`，前面的阶段负责"编译打包"，最后一个阶段只把"产物"拷过来，扔掉所有构建工具。**

类比：**在装备齐全的大厨房（构建阶段）里做好菜，然后只把成品菜端到餐桌（运行阶段）上，厨房的锅碗瓢盆全留在后面不带走。**

### 例子一：前端项目（Vite/React/Vue 通用）

```dockerfile
# ---------- 阶段 1：构建（起个名字叫 builder）----------
FROM node:20-alpine AS builder
#   AS builder 给这个阶段命名，后面要引用它

WORKDIR /app
COPY package*.json ./
RUN npm ci                    # 装全部依赖（含 devDependencies，构建需要）
COPY . .
RUN npm run build             # 执行打包，产物通常在 /app/dist 目录

# ---------- 阶段 2：运行（最终镜像）----------
FROM nginx:1.27-alpine
#   全新的、干净的 nginx 镜像，和上面的 builder 毫无关系

COPY --from=builder /app/dist /usr/share/nginx/html
#   ★ 关键：--from=builder 表示"从 builder 阶段"拷贝
#   把 builder 里打包好的 /app/dist，拷到 nginx 的网站根目录
#   ★ 最终镜像里【只有 nginx + 静态文件】，没有 Node、没有 node_modules！

EXPOSE 80
# nginx 镜像自带了启动命令，无需再写 CMD
```

**效果**：最终镜像里完全没有 Node 和源码，只有一个 Nginx（约 50MB）加上你那几 MB 的静态文件。而如果不用多阶段，光 node_modules 就可能几百 MB。

### 例子二：Go 项目（你会更爱这个）

```dockerfile
# ---------- 阶段 1：编译 ----------
FROM golang:1.22-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download            # 先下依赖（利用缓存，同 4.2 思路）
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server .
#   CGO_ENABLED=0 编译成【纯静态二进制】，不依赖系统 C 库，能在极简镜像里跑
#   -o /app/server 输出二进制到 /app/server

# ---------- 阶段 2：运行 ----------
FROM alpine:3.20
#   甚至可以用 scratch（空镜像）或 distrolss，但 alpine 方便调试
COPY --from=builder /app/server /server
#   只把编译好的二进制拷过来

EXPOSE 8080
CMD ["/server"]
```

**效果**：Go 的最终镜像可以做到 **10~20MB**（甚至用 `scratch` 做到 5MB 以内），而带着整个 Go SDK 的镜像有 **800MB+**。差距 50 倍。

## 4.4 选基础镜像的学问

`FROM` 用哪个基础镜像，直接决定体积、安全性和调试便利度。常见后缀：

| 变体 | 基于 | 体积 | 特点 | 适用 |
|------|------|------|------|------|
| （无后缀）如 `node:20` | Debian 完整版 | 大（~1GB） | 工具齐全，啥都有 | 需要编译原生模块、要调试时 |
| `-slim` 如 `node:20-slim` | Debian 精简版 | 中（~200MB） | 砍掉大部分不常用工具 | 通用生产环境的稳妥选择 |
| `-alpine` 如 `node:20-alpine` | Alpine Linux | 小（~50MB 基础） | 极小，但用 musl libc | 追求小体积，多数场景 OK |
| `distroless` | Google 出品 | 极小 | 只有运行时，没 shell | 安全要求高的生产（没 shell 更难被攻击） |
| `scratch` | 空 | 0 | 什么都没有 | 纯静态二进制（如 Go） |

⚠️ **Alpine 的坑**：Alpine 用的是 `musl` libc 而非主流的 `glibc`。绝大多数情况没问题，但**某些依赖预编译 glibc 二进制的 npm 包（或特定的原生模块）在 alpine 上可能报错**（比如某些老版本的 `bcrypt`、`sharp`）。遇到诡异的原生模块编译错误，先怀疑 alpine，可换回 `-slim` 试试。

> 💡 **给你的默认建议**：
> - Node 应用：先用 `node:20-alpine`，遇到原生模块问题就换 `node:20-slim`。
> - Go 应用：`golang:1.22-alpine` 构建 + `alpine:3.20` 或 `scratch` 运行。
> - ⚠️ 别用无后缀的完整版跑生产，太臃肿。

## 4.5 镜像瘦身实测对比

以我们的实战后端为例，感受优化前后的差距（数字为大致量级）：

| 方案 | 大致体积 | 说明 |
|------|---------|------|
| `FROM node:20`（完整版）+ 拷了 node_modules | ~1.1 GB | 又肥又慢 |
| `FROM node:20-alpine` + `npm ci`（第 3 章的写法） | ~180 MB | 已经不错 |
| 多阶段 + 只保留生产依赖 | ~130 MB | 更精简 |
| Go 多阶段 + alpine 运行 | ~15 MB | 极致 |

**优化的三板斧**：

1. **选对基础镜像**（alpine / slim / distroless）。
2. **多阶段构建**，把构建工具留在前一阶段。
3. **合并 RUN、清理缓存**：比如 `RUN apt-get update && apt-get install -y xxx && rm -rf /var/lib/apt/lists/*`，装完就在**同一层**删缓存（分成两层删是没用的，因为上一层的文件还留在历史里）。

## 4.6 🔨 实战项目推进②：多阶段构建打包前端

我们给实战项目加一个前端，用多阶段构建把它做成一个小巧的 Nginx 镜像。

**第 1 步：创建最小前端项目**

新建目录 `todo-frontend`，建文件：

`package.json`：
```json
{
  "name": "todo-frontend",
  "version": "1.0.0",
  "scripts": { "build": "vite build" },
  "devDependencies": { "vite": "^5.4.0" }
}
```

`index.html`：
```html
<!DOCTYPE html>
<html>
  <head><title>Todo App</title></head>
  <body>
    <h1>📝 My Todo App</h1>
    <p>前端已通过多阶段构建打包并由 Nginx 托管！</p>
    <script type="module" src="/main.js"></script>
  </body>
</html>
```

`main.js`：
```javascript
console.log('Frontend loaded 🚀');
document.body.style.fontFamily = 'system-ui';
```

`.dockerignore`：
```gitignore
node_modules
dist
.git
```

**第 2 步：写多阶段 Dockerfile**（`todo-frontend/Dockerfile`）：

```dockerfile
# ---------- 阶段 1：用 Node 打包 ----------
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install               # 装构建依赖（vite）
COPY . .
RUN npm run build             # vite 打包，产物在 /app/dist

# ---------- 阶段 2：用 Nginx 托管产物 ----------
FROM nginx:1.27-alpine
COPY --from=builder /app/dist /usr/share/nginx/html
#   只把 dist 拷进 nginx，最终镜像不含 Node
EXPOSE 80
```

**第 3 步：构建并对比体积**

```bash
docker build -t todo-frontend:1.0 .
docker images | grep todo-frontend
#   预期：体积在 50MB 左右（主要是 nginx alpine + 你的几个小文件）
```

**第 4 步：运行验证**

```bash
docker run -d --name todo-web -p 8080:80 todo-frontend:1.0
#   后台运行，宿主机 8080 → 容器 80
```

浏览器访问 <http://localhost:8080>：

✅ **预期输出**：页面显示 **"📝 My Todo App"** 和那句说明文字，打开浏览器控制台能看到 `Frontend loaded 🚀`。

**第 5 步：验证"最终镜像里真的没有 Node"**

```bash
docker run --rm todo-frontend:1.0 node -v
#   预期：报错 "node: not found" 或 executable file not found
#   ★ 这正是我们要的！证明最终镜像里完全没有 Node，多阶段构建成功把它甩掉了。
```

清理：
```bash
docker rm -f todo-web
```

> 🎯 **自检**：你能解释为什么最终镜像里没有 Node 吗？（答：因为 Node 只存在于 `builder` 阶段；最终阶段 `FROM nginx` 是全新的镜像，只通过 `--from=builder` 拷了 `dist` 静态文件过来，没拷 Node。）

## ✅ 本章小结

- **层缓存核心规则**：某层输入不变就复用缓存；一层失效，其后所有层全部重建。所以**指令顺序决定构建速度**。
- **依赖安装黄金法则**：先 `COPY package.json` + 装依赖，再 `COPY` 源码。让"不常变的"在前，"常变的"在后。
- **多阶段构建**：前一阶段编译打包，最后阶段只 `COPY --from=` 拷产物，把构建工具全甩掉。前端 → Nginx 托管静态文件；Go → 只留二进制。
- **基础镜像选择**：alpine 最小（注意 musl 坑）、slim 稳妥、distroless/scratch 极致安全小巧。
- 你的前端镜像现在只有 ~50MB，且不含 Node——这就是专业镜像的样子。
