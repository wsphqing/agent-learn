# 第 11 章 · 通往 K8s 的桥梁

> 本章目标：把你已经掌握的 Docker 概念映射到 Kubernetes，理解"为什么 Compose 还不够"，为下一阶段学习铺好路。

---

## 11.1 你已经掌握的 Docker 概念，在 K8s 里对应什么

这是最让人安心的一点：**K8s 不是全新的一套东西，而是把你已经会的东西"升级到集群规模"。** 概念是连续的。

| 你在 Docker 里学的 | Kubernetes 里对应的 | 说明 |
|-------------------|-------------------|------|
| 容器（Container） | **Pod** | K8s 最小调度单位。一个 Pod 通常装一个容器（偶尔多个紧密相关的容器） |
| `docker run` | **Deployment / Pod** | 声明"要跑几个副本、用什么镜像"，K8s 负责维持这个状态 |
| Dockerfile / 镜像 | **不变**（还是镜像） | K8s 用的就是 Docker 镜像！你第 8 章推的镜像直接用 |
| 数据卷（Volume） | **PersistentVolume (PV) / PVC** | 概念一致：把存储与容器解耦。只是集群里更复杂（多节点、动态供给） |
| Docker 网络 + 服务名 | **Service** | 给一组 Pod 一个稳定的访问入口名，类似我们 Compose 里的服务名 |
| `-p 8080:80` 端口映射 | **Service / Ingress** | 对外暴露服务的方式 |
| Compose 的 `depends_on` | **探针（liveness/readiness probe）** | K8s 用健康探针判断 Pod 是否就绪、是否需要重启 |
| `restart: always` | **内置自愈（ReplicaSet）** | K8s 天生就会维持期望副本数、自动重建挂掉的 Pod |
| `docker compose up` | **`kubectl apply -f xxx.yaml`** | 都是"声明式地描述期望状态，一条命令让它成真" |
| `docker-compose.yml` | **一堆 K8s YAML（Deployment/Service/…）** | 同样是声明式 YAML，字段更多更强大 |

> 💡 **一句话**：**K8s = Docker 概念 + 集群化 + 声明式自愈 + 自动扩缩容。** 你会 Docker，学 K8s 就绕过了一大半"底层是什么"的困惑。

---

## 11.2 为什么有了 Compose 还需要 K8s

一个自然的疑问：**Compose 不是挺好用吗，为什么还要 K8s？** 关键在于**规模**和**可靠性要求**：

| 维度 | Docker Compose | Kubernetes |
|------|---------------|------------|
| 运行范围 | **单机**（一台机器上） | **集群**（成百上千台机器） |
| 高可用 | 机器挂了全挂 | 某台挂了，Pod 自动调度到别的机器 |
| 扩缩容 | 手动（改配置重启） | 一条命令横向扩到 N 个副本，甚至自动按负载扩缩 |
| 滚动更新/回滚 | 粗糙（就是重建） | 完善的滚动更新、灰度、一键回滚 |
| 服务发现/负载均衡 | 基础（服务名直连单实例） | 内置服务发现 + 多副本负载均衡 |
| 自愈 | 靠 `restart` 策略 | 持续把实际状态纠偏到期望状态 |
| 适用 | **单机部署、开发环境、小项目** | **生产、大规模、高可用场景** |

**结论**：

- **单台服务器、中小项目**：Docker Compose **完全够用**，甚至更简单直接。别为了用 K8s 而用 K8s。
- **多台机器、要高可用、要弹性伸缩、团队规模大**：K8s 的价值才真正体现。

> 💡 你现在的判断力：**能根据需求选对工具**，比盲目上 K8s 更专业。很多公司的小服务用 Compose + 单机跑得好好的。

## 11.3 下一步学习路线建议

既然目标是"为学 K8s 打基础"，按这个顺序往下走最顺：

**第一步：先在单机上把 Docker 用到熟练**
- 用本文档的实战项目**反复练习**：改代码 → 构建 → 部署 → 排错。
- 尝试给别人（或自己另一个项目）做容器化，直到 Dockerfile 和 Compose 写得得心应手。
- 用 `docker compose` 搭几个你熟悉的中间件（MySQL、MongoDB、RabbitMQ、Kafka）来练手——很实用。

**第二步：学本地 K8s 环境（免费、零成本）**
- **Docker Desktop 自带 Kubernetes**：设置里勾选 "Enable Kubernetes" 就能在本地起一个单节点集群，**不用装任何东西**就能开始练 `kubectl`。★ 最省事的起点。
- 或 **minikube** / **kind**：更灵活的本地集群工具（kind 用 Docker 容器跑 K8s，很适合练习）。

**第三步：学习 K8s 核心对象（按此顺序）**
1. **Pod**：最小单位，理解它和容器的关系。
2. **Deployment**：管理 Pod 副本、滚动更新。
3. **Service**：给 Pod 组一个稳定入口（对应 Compose 的服务名）。
4. **ConfigMap / Secret**：配置和密钥注入（对应 Docker 的 `-e` / `.env`，但更规范）。
5. **PersistentVolume / PVC**：持久化存储（对应 Docker 数据卷）。
6. **Ingress**：对外暴露 HTTP 路由（对应我们第 9 章的 Nginx 反代）。

**第四步：把实战项目搬上 K8s**
- 把第 9 章的 todo-app 从 Compose 改写成 K8s YAML（Deployment + Service + PVC），部署到本地 minikube/kind。**你会发现自己几乎只是在"翻译"已知概念**，学习曲线大幅平缓。

**第五步：进阶**
- Helm（K8s 的包管理，类似 Compose 之于 Docker）
- CI/CD 集成（GitHub Actions 构建镜像 → 推仓库 → 部署）
- 监控（Prometheus + Grafana）、日志（EFK）

**推荐资源**：
- Kubernetes 官方文档（概念部分写得极好）
- 《Kubernetes 权威指南》（书）
- Katacoda / Killercoda 在线交互实验环境（浏览器里练 K8s，不用装）

## ✅ 本章小结

- **K8s 概念和 Docker 是连续的**：容器→Pod、`docker run`→Deployment、数据卷→PV/PVC、服务名→Service、`restart`→自愈。你学的每一样都有对应。
- **Compose 适合单机/中小项目；K8s 适合多机/高可用/弹性场景。** 按需选型，别盲目上 K8s。
- **下一步**：Docker 练熟 → Docker Desktop 开本地 K8s → 学 Pod/Deployment/Service/PVC → 把实战项目搬上 K8s。
- 你会 Docker，学 K8s 已经领先一大截了。
