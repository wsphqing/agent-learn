# 第 5 章 · 数据持久化：数据卷与挂载

> 本章目标：解决"容器一删数据就没了"的致命问题，搞懂数据卷 vs 绑定挂载，并用绑定挂载实现开发时的**代码热更新**。

---

## 5.1 核心痛点：容器是"用完即弃"的

回顾第 2 章：容器 = 镜像的只读层 + **一个可写层**。容器运行时产生的所有数据（数据库文件、上传的图片、日志）都写在那个**可写层**里。

⚠️ **可写层的命运和容器绑定：容器一删（`docker rm`），可写层连同里面所有数据一起灰飞烟灭。**

想象一下：你用容器跑了个 Postgres，存了一堆数据。某天你想升级，`docker rm` 删了旧容器换新的——**所有数据没了**。这显然不能接受。

**根本原因**：Docker 的设计哲学是"容器应该是**无状态、可随时销毁重建**的"。那"状态"（数据）该放哪？答案是：**放到容器外面去**。这就是数据持久化。

Docker 提供两种主要方式把数据放到容器外：**数据卷（Volume）** 和 **绑定挂载（Bind Mount）**。

---

## 5.2 数据卷（Volume）

> **数据卷 = 由 Docker 管理的、独立于容器生命周期的一块存储区。**

生活类比：数据卷就像**银行的保险柜**。你的容器（你）可以来来去去、生生死死，但保险柜（数据卷）由银行（Docker）统一保管在专门的地方，容器删了，保险柜和里面的东西还在。下次新容器可以再"挂载"上这个保险柜，接着用里面的数据。

**特点**：

- 由 Docker 创建和管理，存放在 Docker 的专属目录里（你不用关心具体在哪）。
- 独立于容器，**容器删了卷还在**。
- 跨平台一致、性能好，是**存数据库数据的首选**。

**使用场景**：数据库数据、需要长期保存且不需要你手动编辑的数据。

```bash
docker volume create mydata          # ← 手动创建一个卷（也可运行容器时自动创建）
docker volume ls                     # ← 列出所有卷
docker volume inspect mydata         # ← 查看卷的详情（挂载点路径等）
docker volume rm mydata              # ← 删除卷
```

挂载到容器：

```bash
docker run -d --name pg \
  -v mydata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret \
  postgres:16
# 关键参数 -v mydata:/var/lib/postgresql/data 解释：
#   冒号左边 mydata = 数据卷的名字（不是路径！这是它和绑定挂载的关键区别）
#   冒号右边 /var/lib/postgresql/data = 容器【内部】Postgres 存数据的目录
#   效果：Postgres 写到那个目录的数据，实际存进了名为 mydata 的卷里，与容器解耦
```

---

## 5.3 绑定挂载（Bind Mount）

> **绑定挂载 = 把你【宿主机上的一个具体目录】直接映射进容器。**

生活类比：绑定挂载就像**共享文件夹 / 一扇任意门**。宿主机上的某个文件夹和容器里的某个路径变成"同一个地方"，你在宿主机改文件，容器里立刻能看到；容器里改，宿主机也变。

**特点**：

- 你**明确指定宿主机的哪个目录**。
- 宿主机和容器**实时双向同步**（本质是同一份文件）。
- 依赖宿主机的目录结构。

**使用场景**：
- **开发时代码热更新**（改宿主机代码，容器内立即生效，不用重新 build）★ 这是我们最爱用的场景。
- 需要把宿主机的配置文件塞进容器（比如 nginx 配置）。

```bash
docker run -d --name dev \
  -v $(pwd):/app \
  node:20-alpine \
  sh -c "cd /app && npm run dev"
# 关键参数 -v $(pwd):/app 解释：
#   冒号左边 $(pwd) = 宿主机当前目录的【绝对路径】（$(pwd) 会展开成 /Users/you/xxx）
#   冒号右边 /app = 容器内的目录
#   ★ 判断是"卷"还是"绑定挂载"的诀窍：左边是【路径】(以 / 或 . 开头) → 绑定挂载；
#     左边是【名字】(如 mydata) → 数据卷。
```

⚠️ **macOS 专属提醒**：`-v` 左边**必须是绝对路径**。用 `$(pwd)` 自动展开是最稳的写法。写相对路径可能被 Docker 误判成"卷名"。

---

## 5.4 ⚠️ 对比表：数据卷 vs 绑定挂载 vs tmpfs

| 维度 | 数据卷（Volume） | 绑定挂载（Bind Mount） | tmpfs |
|------|-----------------|----------------------|-------|
| **谁管理** | Docker 管理 | 你指定宿主机路径 | 内存 |
| **`-v` 左边写什么** | 卷名（如 `mydata`） | 宿主机绝对路径（如 `$(pwd)`） | 无 |
| **存在哪** | Docker 专属目录 | 你指定的宿主机目录 | 宿主机内存（不落盘） |
| **容器删除后数据** | ✅ 保留 | ✅ 保留（在宿主机上） | ❌ 消失 |
| **宿主机能否直接看/改** | 不方便（在 Docker 内部目录） | ✅ 方便，就是普通文件夹 | 不适用 |
| **典型用途** | 数据库数据等持久化 | 开发热更新、注入配置 | 存临时敏感数据、缓存 |
| **性能（macOS）** | 好 | ⚠️ 较差（跨 VM 同步开销） | 最快 |

**怎么选（一句话决策）**：

- 存**数据库/需要长期保存**的数据 → **数据卷**。
- 开发时想**改代码立即生效** / 注入配置文件 → **绑定挂载**。
- 只是临时的、不想落盘的敏感数据 → tmpfs（少用，了解即可）。

---

## 5.5 `-v` 与 `--mount` 两种写法

Docker 挂载有两种语法，`-v`（简写）和 `--mount`（显式）。

```bash
# -v 写法（简洁，老手常用）
-v mydata:/var/lib/postgresql/data          # 数据卷
-v $(pwd):/app                              # 绑定挂载
-v $(pwd)/config.conf:/etc/app/config.conf  # 挂单个文件也行
-v mydata:/data:ro                          # 结尾加 :ro 表示只读（read-only）

# --mount 写法（啰嗦但清晰，不易出错，官方推荐生产用）
--mount type=volume,source=mydata,target=/var/lib/postgresql/data
--mount type=bind,source=$(pwd),target=/app
--mount type=bind,source=$(pwd),target=/app,readonly
#   type      volume(数据卷) / bind(绑定挂载) / tmpfs
#   source    卷名 或 宿主机路径
#   target    容器内路径
```

⚠️ **`-v` 的一个隐蔽坑**：用 `-v` 做绑定挂载时，**如果宿主机路径不存在，Docker 会自动创建一个空目录**（而不是报错），容易让你莫名其妙。而 `--mount` 在路径不存在时会**直接报错**，更安全。新手用 `-v` 图方便没问题，但记住这个差异。

## 5.6 开发神器：用绑定挂载实现代码热更新

这是绑定挂载对你日常开发最有价值的用法。

**问题**：开发时每改一行代码就要 `docker build` + `docker run`，慢到崩溃。

**解法**：把源码目录**绑定挂载**进容器，容器里跑一个"监听文件变化自动重启"的工具（如 `nodemon`）。这样你在宿主机（用你熟悉的 VS Code）改代码，容器里的服务**自动重启**，秒级生效，完全不用重新 build。

```bash
docker run -d --name todo-dev \
  -p 3000:3000 \
  -v $(pwd):/app \
  -v /app/node_modules \
  -w /app \
  node:20-alpine \
  sh -c "npm install && npx nodemon server.js"
# 逐个参数解释：
#   -p 3000:3000            端口映射
#   -v $(pwd):/app          ★ 把宿主机当前目录挂进容器 /app，实现代码同步
#   -v /app/node_modules    ★★ 关键技巧！见下方"坑2"详解——用一个匿名卷"保护"容器内的 node_modules
#   -w /app                 设置工作目录（等价于 Dockerfile 里的 WORKDIR）
#   sh -c "..."             容器启动后执行的命令：装依赖并用 nodemon 启动（会监听文件变化自动重启）
```

之后你在宿主机改 `server.js`，容器日志里会看到 nodemon 打印 `restarting due to changes...`，改动立即生效。

## 5.7 ⚠️ 常见坑

**坑 1：挂载后容器内原有文件"消失"了**
如果容器内 `/app` 本来有文件，你又把宿主机一个**空目录**绑定挂载到 `/app`，那么容器内 `/app` 会被宿主机的空目录**盖住**，原文件看不见了（并没删除，只是被遮挡）。这是挂载的正常行为——**挂载点会用宿主机内容覆盖容器内该路径**。

**坑 2：绑定挂载把容器里的 node_modules 也覆盖了**（超高频坑）
承接坑 1：你 `-v $(pwd):/app` 把宿主机项目挂进去，但宿主机的 `/app` 里**没有 node_modules**（或有的是 macOS 版的），结果容器内镜像里装好的 Linux 版 node_modules 被盖没了 → 应用报"找不到模块"。
**解法**：再加一个 `-v /app/node_modules`（一个匿名卷）。它的作用是**在宿主机覆盖之上，再把容器内的 /app/node_modules 单独"保护"起来**，用镜像里那份，不被宿主机盖掉。这就是 5.6 里那行 `-v /app/node_modules` 的意义。

**坑 3：macOS 上绑定挂载很慢**
因为 macOS 的容器跑在 Linux 虚拟机里（第 0 章），宿主机和 VM 之间的文件同步有开销。大量文件读写（比如挂载巨大的 node_modules 目录）会明显变慢。
**缓解**：① 用坑 2 的技巧让 node_modules 走匿名卷而非绑定挂载；② `-v` 加 `:cached` 或 `:delegated` 后缀（新版 Docker Desktop 已优化，影响变小）；③ 数据库数据用**数据卷**而非绑定挂载。

**坑 4：权限问题（Permission denied）**
容器里进程的用户（可能是 root 或某个特定 uid）和宿主机文件的属主 uid 不一致，导致读写报权限错。Linux 上更常见，macOS 上 Docker Desktop 做了处理相对少见。遇到时可用 Dockerfile 里的 `USER` 或挂载时调整权限解决。

## 5.8 🔨 实战项目推进③：给应用接一个数据库

我们给实战项目加上 Postgres，并用**数据卷**保证数据"重启不丢、删容器也不丢"。

**第 1 步：用数据卷启动 Postgres**

```bash
docker run -d --name todo-db \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=tododb \
  -v todo-pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:16
# 参数解释：
#   -e POSTGRES_PASSWORD=secret  设置数据库超级用户密码（postgres 镜像要求必须设）
#   -e POSTGRES_DB=tododb        初始化时创建一个名为 tododb 的数据库
#   -v todo-pgdata:/var/lib/postgresql/data  ★ 用名为 todo-pgdata 的数据卷存数据目录
#   -p 5432:5432                 映射数据库端口（方便你用本地工具连）
```

确认卷已自动创建：
```bash
docker volume ls | grep todo-pgdata     # ← 预期能看到 todo-pgdata
```

**第 2 步：写入一些数据**

```bash
docker exec -it todo-db psql -U postgres -d tododb
#   进入容器内的 psql 客户端，-U postgres 用户，-d tododb 数据库
```

在 psql 提示符里执行：
```sql
CREATE TABLE todos (id SERIAL PRIMARY KEY, title TEXT);
INSERT INTO todos (title) VALUES ('学习 Docker'), ('搞定数据卷');
SELECT * FROM todos;
```
✅ **预期输出**：显示两行数据（学习 Docker / 搞定数据卷）。然后 `\q` 退出 psql。

**第 3 步：见证奇迹——删掉容器，数据还在**

```bash
docker rm -f todo-db          # ← 把数据库容器彻底删除！
docker volume ls | grep todo-pgdata   # ← 卷 todo-pgdata 还在（数据的真身在这）
```

现在用**同一个卷**起一个**全新的**容器：
```bash
docker run -d --name todo-db-new \
  -e POSTGRES_PASSWORD=secret \
  -v todo-pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:16
#   注意：容器名换成了 todo-db-new，但挂的是同一个卷 todo-pgdata
```

查数据还在不在：
```bash
docker exec -it todo-db-new psql -U postgres -d tododb -c "SELECT * FROM todos;"
#   -c "SQL" 表示执行一条 SQL 后立即退出
```

✅ **预期输出**：**依然显示"学习 Docker / 搞定数据卷"两行数据！** 尽管旧容器已经被删、这是个全新容器，数据却完好无损——因为数据活在**卷**里，不在容器里。这就是数据持久化的意义。

**对比实验（可选，加深理解）**：如果第 1 步你**不加 `-v`**，那么第 3 步删容器后数据就真的没了。你可以亲手试一次，感受"有卷"和"无卷"的天壤之别。

清理（保留卷，第 7 章还要用）：
```bash
docker rm -f todo-db-new
# 想彻底删数据：docker volume rm todo-pgdata（现在先别删）
```

> 🎯 **自检**：为什么删了容器数据还在？你能说出 `-v todo-pgdata:/var/lib/postgresql/data` 里冒号两边分别是什么吗？（左边是卷名，右边是容器内 Postgres 存数据的目录。）

## ✅ 本章小结

- 容器的可写层**随容器删除而消失**，所以**有状态数据必须放到容器外**。
- **数据卷（Volume）**：Docker 管理的"保险柜"，独立于容器，**存数据库数据的首选**。`-v 卷名:容器路径`。
- **绑定挂载（Bind Mount）**：宿主机目录直连容器，双向实时同步，**开发热更新和注入配置的利器**。`-v 宿主机绝对路径:容器路径`。
- 判断诀窍：`-v` 左边是**名字**→卷；是**路径**→绑定挂载。
- ⚠️ 重点坑：绑定挂载会覆盖容器内同路径 → 用 `-v /app/node_modules` 匿名卷保护依赖；macOS 挂载偏慢。
- 你的实战项目现在有了一个数据不会丢的数据库。
