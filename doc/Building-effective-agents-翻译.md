> **说明：** 本文所述的工具生态自 2024 年 12 月以来已发生较大变化。关于我们当前的做法，请参阅 [我们如何构建 Claude 托管智能体（how we built Claude Managed Agents）](https://www.anthropic.com/engineering/managed-agents) 以及 [托管智能体（Managed Agents）文档](https://platform.claude.com/docs/en/managed-agents/overview)。

在过去一年中，我们与数十个团队合作，在众多行业中构建基于大语言模型（LLM）的智能体。一个始终如一的规律是：最成功的实现，往往并没有使用复杂的框架或专门的库，而是基于简单、可组合的模式构建而成。

在本文中，我们将分享与客户合作以及自行构建智能体过程中积累的经验，并为开发者提供构建有效智能体的实用建议。

## 什么是智能体？

“智能体”（Agent）一词有多种定义方式。有些客户将其理解为完全自主运行、能在较长时间内独立行动、借助各种工具完成复杂任务的系统；另一些客户则用该词来描述遵循预定义工作流的、更具规则性的实现。在 Anthropic，我们将所有这些形态统称为**智能体系统（agentic systems）**，但在架构上做出一个重要区分——**工作流（workflows）** 与**智能体（agents）**：

- **工作流（Workflows）**：通过预定义的代码路径来编排 LLM 与工具的系统。
- **智能体（Agents）**：LLM 动态地主导自身执行过程与工具使用方式、自主掌控任务完成路径的系统。

下文我们将逐一深入探讨这两类智能体系统。在附录 1（“实践中的智能体”）中，我们将介绍两个客户发现这类系统价值尤为突出的领域。

## 何时使用（以及何时不使用）智能体

在基于 LLM 构建应用时，我们建议先寻找最简单的解决方案，仅在确有需要时才增加复杂性。这甚至意味着——完全可以完全不构建智能体系统。智能体系统通常会以更高的延迟和成本换取更好的任务表现，你需要权衡这种取舍是否合理。

当确实需要更高的复杂性时：对于定义清晰的任务，工作流能提供可预测性与一致性；而当需要大规模地依赖灵活性与模型驱动的决策时，智能体则是更优的选择。不过对于许多应用而言，仅仅通过检索（retrieval）和上下文内示例（in-context examples）来优化单次 LLM 调用，通常就已经足够了。

## 何时以及如何使用框架

有许多框架能让智能体系统更易于实现，其中包括：

- [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)；
- [AWS 的 Strands Agents SDK](https://strandsagents.com/latest/)；
- [Rivet](https://rivet.ironcladapp.com/)，一款拖拽式 GUI（图形界面）LLM 工作流构建工具；以及
- [Vellum](https://www.vellum.ai/)，另一款用于构建与测试复杂工作流的 GUI 工具。

这些框架通过简化底层常规任务（如调用 LLM、定义与解析工具、串联调用等），让入门变得容易。然而，它们往往会引入额外的抽象层，遮蔽底层的提示词（prompt）与响应，从而加大调试难度。它们还可能诱使人们在更简单的方案已足够的情况下，不必要地增加复杂性。

我们建议开发者直接使用 LLM API 起步：许多模式用几行代码就能实现。如果你确实使用框架，请务必理解其底层代码。对框架“黑盒”内部机制的想当然假设，是客户出错的一个常见根源。

如需示例实现，请参阅我们的 [cookbook](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

## 构建模块、工作流与智能体

在本节中，我们将探讨在生产环境中见到的智能体系统的常见模式。我们将从最基础的构建模块——增强型 LLM——开始，逐步提升复杂性，从简单的组合式工作流一路讲到自主智能体。

### 构建模块：增强型 LLM（The augmented LLM）

智能体系统的基本构建模块，是一个经过检索、工具、记忆等增强能力加持的 LLM。我们当前的模型能够主动使用这些能力——自行生成搜索查询、选择恰当的工具，并自行决定需要保留哪些信息。

![增强型 LLM](https://www-cdn.anthropic.com/images/4zrzovbb/website/d3083d3f40bb2b6f477901cc9a240738d3dd1371-2401x1000.png)

*图：增强型 LLM（The augmented LLM）*

我们建议在实现时重点关注两个方面：将这些能力针对你的具体用例进行定制，并确保它们为 LLM 提供简单、文档完善的接口。实现这些增强能力的方法有很多，其中一种是通过我们近期发布的 [模型上下文协议（Model Context Protocol，MCP）](https://www.anthropic.com/news/model-context-protocol)，它使开发者能够通过一个简单的 [客户端实现](https://modelcontextprotocol.io/tutorials/building-a-client#building-mcp-clients) 接入日益壮大的第三方工具生态。

在下文剩余部分，我们假定每次 LLM 调用都能访问这些增强能力。

### 工作流：提示链（Prompt chaining）

提示链将任务分解为一系列步骤，每一步的 LLM 调用都对上一步的输出进行处理。你可以在任意中间步骤添加程序化的检查（见下图中的 “gate”，即“闸门”），以确保流程仍在正轨上。

![提示链工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/7418719e3dab222dccb379b8879e1dc08ad34c78-2401x1000.png)

*图：提示链工作流（The prompt chaining workflow）*

**何时使用该工作流：** 当任务可以被轻松、清晰地将任务分解为固定子任务时，此工作流最为理想。其主要目标是用延迟换取更高的准确率——让每次 LLM 调用都处理一个更简单的任务。

**提示链有用的示例：**

- 生成营销文案，然后将其翻译成另一种语言。
- 先写出文档大纲，检查大纲是否符合特定标准，再基于大纲撰写文档正文。

### 工作流：路由（Routing）

路由对输入进行分类，并将其导向专门的后续任务。该工作流实现了关注点分离（separation of concerns），并能构建更专门化的提示词。若缺少该工作流，针对某一类输入的优化可能会损害其他类型输入的表现。

![路由工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/5c0c0e9fe4def0b584c04d37849941da55e5e71c-2401x1000.png)

*图：路由工作流（The routing workflow）*

**何时使用该工作流：** 对于存在明显不同类别、且各类别更适合分别处理的复杂任务，路由非常有效；同时也要求分类能够被准确完成——无论是由 LLM，还是由更传统的分类模型/算法来承担。

**路由有用的示例：**

- 将不同类型的客户服务咨询（一般性问题、退款申请、技术支持）导向不同的下游流程、提示词与工具。
- 将简单/常见的问题路由到更小、更具成本效益的模型（如 Claude Haiku 4.5），将困难/不寻常的问题路由到能力更强的模型（如 Claude Sonnet 4.5），以实现最佳性能优化。

### 工作流：并行化（Parallelization）

有时可以让多个 LLM 同时处理一项任务，并以程序化方式聚合它们的输出。这种被称为**并行化**的工作流有两种关键变体：

- **分段（Sectioning）：** 将任务拆分为相互独立的子任务并行执行。
- **投票（Voting）：** 对同一任务多次运行，以获得多样化的输出。

![并行化工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/406bb032ca007fd1624f261af717d70e6ca86286-2401x1000.png)

*图：并行化工作流（The parallelization workflow）*

**何时使用该工作流：** 当拆分出的子任务可以并行执行以提升速度时，或是当需要多角度审视、多次尝试以提升结果置信度时，并行化是有效的。对于需要权衡多个因素的复杂任务，LLM 通常在被拆分为独立的 LLM 调用、让每次调用专注于某一方面时表现更好，从而对每个具体方面给予专注的注意力。

**并行化有用的示例：**

- **分段：**
  - 实现护栏（guardrails）：一个模型实例处理用户查询，另一个模型实例筛查其中的不当内容或请求。这通常比让同一次 LLM 调用同时处理护栏与核心响应效果更好。
  - 自动化评估（evals）以衡量 LLM 性能：每次 LLM 调用从不同维度评估模型在给定提示词上的表现。
- **投票：**
  - 审查一段代码中的漏洞：多个不同的提示词分别进行审查，发现问题时予以标记。
  - 评估某段内容是否不当：多个提示词从不同角度评估，或要求达到不同的投票阈值，以在误报与漏报之间取得平衡。

### 工作流：编排器-执行者（Orchestrator-workers）

在编排器-执行者工作流中，一个中央 LLM 动态地拆解任务，将其委派给多个执行者 LLM，并整合它们的结果。

![编排器-执行者工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/8985fc683fae4780fb34eab1365ab78c7e51bc8e-2401x1000.png)

*图：编排器-执行者工作流（The orchestrator-workers workflow）*

**何时使用该工作流：** 当任务所需的子任务难以预先预测时（例如在编码场景下，需要修改的文件数量、以及每个文件所需修改的性质，往往取决于具体任务本身），该工作流非常合适。尽管它与并行化在结构上相似，但关键在于其灵活性——子任务并非预先定义，而是由编排器根据具体输入动态决定。

**编排器-执行者有用的示例：**

- 每次都需要对多个文件进行复杂修改的编码类产品。
- 需要从多个来源收集并分析信息、以寻找可能相关信息的搜索任务。

### 工作流：评估器-优化器（Evaluator-optimizer）

在评估器-优化器工作流中，一次 LLM 调用负责生成响应，另一次 LLM 调用则在循环中提供评估与反馈。

![评估器-优化器工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/14f51e6406ccb29e695da48b17017e899a6119c7-2401x1000.png)

*图：评估器-优化器工作流（The evaluator-optimizer workflow）*

**何时使用该工作流：** 当我们拥有清晰的评估标准，且迭代式改进能带来可衡量的价值时，该工作流尤为有效。判断是否适用的两个标志是：其一，当人类明确表达反馈时，LLM 的响应能否得到可验证的提升；其二，LLM 本身能否提供此类反馈。这类似于人类写作者在打磨一篇成品文章时经历的反复修改过程。

**评估器-优化器有用的示例：**

- 文学翻译：其中存在翻译 LLM 起初可能无法捕捉的细微差异，而评估器 LLM 能提供有益的点评。
- 需要多轮搜索与分析才能收集到全面信息的复杂搜索任务，由评估器决定是否有必要继续搜索。

### 智能体（Agents）

随着 LLM 在关键能力上日趋成熟——理解复杂输入、进行推理与规划、可靠地使用工具、从错误中恢复——智能体正在生产环境中崭露头角。智能体的工作始于人类用户的指令，或与人类用户的交互式讨论。一旦任务明确，智能体便独立地规划与运作，并可能在需要时再次返回人类，以获取更多信息或征询判断。在执行过程中，智能体必须在每一步从环境中获取“真实反馈（ground truth）”（例如工具调用结果或代码执行结果），以评估自身进展。智能体可以在检查点或遇到阻塞时暂停，等待人类反馈。任务通常会在完成后终止，但为了保持可控性，通常也会设置停止条件（例如最大迭代次数）。

智能体能够处理复杂任务，但它们的实现往往相当直白——通常只是在循环中、基于环境反馈使用工具的 LLM。因此，精心且周到地设计工具集及其文档至关重要。关于工具开发的最佳实践，我们在附录 2（“对你的工具做提示工程”）中进行了详细展开。

![自主智能体](https://www-cdn.anthropic.com/images/4zrzovbb/website/58d9f10c985c4eb5d53798dea315f7bb5ab6249e-2401x1000.png)

*图：自主智能体（Autonomous agent）*

**何时使用智能体：** 智能体适用于开放式问题——即难以或无法预测所需步骤数量，且无法硬编码一条固定路径的场景。LLM 可能会运转许多轮次，你必须对其决策能力抱有一定程度的信任。智能体的自主性使其非常适合在可信的环境中规模化地处理任务。

智能体的自主特性意味着更高的成本，以及错误可能不断累积（compounding errors）的风险。我们建议在沙箱环境中进行充分测试，并配以适当的护栏。

**智能体有用的示例：**

以下示例来自我们自己的实现：

- 一个用于解决 [SWE-bench 任务](https://www.anthropic.com/research/swe-bench-sonnet) 的编码智能体，它需要基于任务描述对多个文件进行修改；
- 我们的 [“computer use”（计算机操控）参考实现](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)，其中 Claude 通过操控计算机来完成各项任务。

![编码智能体的高层流程](https://www-cdn.anthropic.com/images/4zrzovbb/website/4b9a1f4eb63d5962a6e1746ac26bbc857cf3474f-2400x1666.png)

## 组合与定制这些模式

这些构建模块并非刻板教条。它们是开发者可以根据不同用例塑形、组合的常见模式。与任何 LLM 特性一样，成功的关键在于衡量性能并迭代实现。再次强调：**只有**当复杂性确实能够改善结果时，你才应该考虑增加它。

## 总结

在 LLM 领域取得成功，并不在于构建最复杂的系统，而在于为你的需求构建**正确**的系统。从简单的提示词开始，通过全面的评估来优化它们，只有当更简单的方案力不从心时，才引入多步骤的智能体系统。

在实现智能体时，我们努力遵循三条核心原则：

1. 在智能体设计中保持**简洁（simplicity）**。
2. 通过显式展示智能体的规划步骤，优先保障**透明性（transparency）**。
3. 通过充分的工具**文档化与测试（documentation and testing）**，精心打造智能体-计算机接口（agent-computer interface，ACI）。

框架能帮助你快速起步，但在向生产环境推进时，不必犹豫去减少抽象层、使用基础组件进行构建。遵循这些原则，你就能打造出不仅强大，而且可靠、可维护、深受用户信赖的智能体。

## 附录 1：实践中的智能体

我们与客户的合作揭示了两个特别有前景的 AI 智能体应用场景，它们体现了上述模式的实际价值。这两个应用都说明：对于那些既需要对话、又需要行动，具有明确成功标准、能够形成反馈闭环，并能融入有意义的人类监督的任务，智能体能够带来最大的价值。

### A. 客户支持（Customer support）

客户支持将大众熟悉的聊天机器人界面与通过工具集成带来的增强能力相结合。它是更开放式智能体的天然用武之地，原因在于：

- 支持类交互天然遵循对话流程，同时又需要访问外部信息与执行操作；
- 可以集成工具来获取客户数据、订单历史与知识库文章；
- 退款、更新工单等操作可以程序化处理；且
- 成功与否可以通过用户自定义的“解决结果”清晰地衡量。

一些公司已通过“按用量计费”的定价模式验证了这一做法的可行性——只对成功解决的案例收费，体现出他们对自家智能体有效性的信心。

### B. 编码智能体（Coding agents）

软件开发领域对 LLM 特性展现出了非凡的潜力，相关能力已从代码补全演进到自主解决问题。智能体在此尤为有效，因为：

- 代码方案可以通过自动化测试进行验证；
- 智能体可以利用测试结果作为反馈来迭代方案；
- 问题空间定义清晰、结构良好；且
- 输出质量可以客观地衡量。

在我们自己的实现中，智能体现在能够仅凭拉取请求（PR）描述，就解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准中的真实 GitHub issue。然而，尽管自动化测试有助于验证功能正确性，人工审查对于确保方案符合更广泛的系统需求仍然至关重要。

## 附录 2：对你的工具做提示工程

无论你在构建哪种智能体系统，工具都很可能成为智能体的重要组成部分。[工具（Tools）](https://www.anthropic.com/news/tool-use-ga) 通过在 API 中精确指定其结构与定义，使 Claude 能够与外部服务和 API 交互。当 Claude 计划调用某工具时，它会在 API 响应中包含一个 [工具调用块（tool use block）](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block)。工具的定义与规范应当受到与整体提示词同等重视的提示工程投入。在本简短附录中，我们介绍如何对你的工具进行提示工程。

同一动作往往有多种指定方式。例如，你可以通过写一个 diff 来指定文件编辑，也可以通过重写整个文件来实现。对于结构化输出，你可以将代码放在 markdown 中，也可以放在 JSON 中返回。在软件工程中，这类差异只是形式上的，可以从一种形式无损转换为另一种。然而，对于 LLM 来说，某些格式的书写难度远高于其他格式。写一个 diff 需要在书写新代码之前知道 chunk 头中要改动的行数；在 JSON 中书写代码（相比 markdown）则需要额外对换行符和引号做转义。

关于如何决定工具格式，我们的建议如下：

- 给模型足够的 token 让它先“思考”，以免它把自己逼入死胡同。
- 让格式尽量接近模型在互联网文本中自然见过的形式。
- 确保不存在格式“开销”，例如需要精确统计数千行代码的行数，或对其写出的任何代码做字符串转义。

一条经验法则是：想想人们在人机交互（HCI）上投入了多少精力，然后规划在打造良好的**智能体**-计算机接口（ACI）上投入同样多的精力。以下是一些如何做的思路：

- **站在模型的角度思考。** 仅根据描述与参数，这个工具的使用方法是否一目了然？还是需要仔细琢磨一番？如果是后者，那么对模型来说很可能也是如此。一个好的工具定义通常包含示例用法、边界情况、输入格式要求，以及与其他工具的清晰界限。
- **如何通过修改参数名称或描述，让一切更加清晰明了？** 不妨把它想象为给团队里的初级开发者写一份出色的 docstring。当存在许多相似工具时，这一点尤为重要。
- **测试模型如何使用你的工具：** 在我们的 [workbench](https://console.anthropic.com/workbench) 中运行大量示例输入，观察模型会犯哪些错误，并据此迭代。
- **对你的工具做“防错（Poka-yoke）”处理。** 调整参数设计，使其更难被误用。

在为 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 构建智能体的过程中，我们实际上在优化工具上花费的时间比优化整体提示词更多。例如，我们发现，当智能体离开根目录后，模型在使用相对文件路径（relative filepaths）的工具时容易出错。为解决此问题，我们将工具改为始终要求绝对文件路径（absolute filepaths）——结果发现模型此后使用该工具时不再出错。
